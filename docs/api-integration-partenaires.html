1.Conventions communes

1.1 URL de base et environnements

Toutes les API décrites dans ce document transitent par un point d'entrée HTTP unique (passerelle Kong) et partagent le préfixe /api :

EnvironnementURL de base
Démonstration localehttp://localhost:8000/api
Production / pilotehttps://<domaine-ou-ip-de-la-plateforme>:8443/api

Un chemin comme /documents/verify/{token_id} dans ce document doit donc être appelé à l'URL complète {URL de base}/documents/verify/{token_id}.

1.2 Authentification (JWT Bearer)

La quasi-totalité des endpoints (à l'exception de ceux explicitement marqués Non) exigent un jeton JWT obtenu via POST /api/auth/login (voir §2), transmis dans l'en-tête HTTP suivant :

Authorization: Bearer <access_token>

Le jeton encode l'identifiant et le rôle applicatif de l'appelant (sub, role) et expire après JWT_EXPIRATION heures (variable d'environnement propre à chaque déploiement — se renseigner auprès de l'exploitant de la plateforme). Un jeton expiré ou invalide produit une réponse 401 Unauthorized.

1.3 Format des requêtes et réponses

ÉlémentConvention
Corps de requêteContent-Type: application/json, sauf mention contraire (upload de fichier en multipart/form-data)
Corps de réponseapplication/json dans tous les cas, y compris les erreurs
DatesISO-8601 avec fuseau (ex. 2026-09-18T10:32:00+00:00)
Identifiants de documentdoc_type + doc_key : référence métier à retenir côté intégrateur (ex. n° de diplôme, de titre foncier) — voir GET /documents/by-reference. token_id : entier, identifiant du NFT ERC-721 on-chain, détail d'implémentation interne utile pour enchaîner sur /versions ou /owner-at
AdressesAdresses Ethereum au format hexadécimal standard (0x...)

1.4 Gestion des erreurs

Toute erreur renvoie un code HTTP standard accompagné d'un corps JSON de la forme {"detail": "message explicite"}. Codes rencontrés dans ce document :

CodeSignification
400Requête invalide (champ manquant, valeur incohérente, règle métier non respectée)
401Authentification absente, invalide ou expirée
403Authentifié mais rôle/droit insuffisant pour cette action
404Ressource introuvable (document, workflow, compte...)
409Conflit avec l'état actuel de la ressource (ex. document déjà transféré)
410Ressource expirée ou révoquée (lien de partage, preuve de divulgation)

1.5 Rôles applicatifs

Chaque compte TrustWedge porte un rôle unique, qui détermine les endpoints accessibles :

RôleType d'acteur
ISSUERÉmetteur de documents (typiquement une université)
VERIFIERVérificateur/émetteur secondaire (typiquement une entreprise)
BANKBanque — instruction de prêts, revue KYC
NOTARYNotaire — validation des transferts de titres, revue KYC
USERCitoyen, titulaire de documents
ADMINAdministrateur de la plateforme (hors périmètre de ce guide — voir §12)

3.Vérification publique de documents

Module verify — point d'intégration principal pour un tiers (recruteur, autre banque, administration...) : lecture directe de la blockchain, sans clé de signature, sans dépendance à la disponibilité de l'émetteur d'origine. La plupart de ces endpoints sont publics, pensés pour être appelés directement depuis le SI d'un tiers (ex. un ATS vérifiant automatiquement un diplôme à la réception d'une candidature).

GET/documents/verify/{token_id}
Authentification requise : Non  ·  Qui : n'importe quel tiers

Vérification canonique d'un document à partir de son identifiant on-chain. Lecture blockchain uniquement (eth_call) — ne peut jamais renvoyer un état falsifié par la plateforme elle-même.

4.Divulgation sélective et partage

Permet à un citoyen de ne divulguer qu'un sous-ensemble des champs d'un document (ex. son nom et son statut de diplômé, sans le détail de ses notes), ou de partager un document entier via un lien à durée de vie limitée. Module exchange.

POST/documents/verify-shared
Authentification requise : Non  ·  Qui : n'importe quel tiers scannant un QR de divulgation sélective

Vérifie une preuve de divulgation sélective générée par le wallet mobile du citoyen (signature ECDSA d'un sous-ensemble de champs). Trois garanties vérifiées dans l'ordre : fraîcheur (preuve valable 5 minutes), authenticité (signature), intégrité (chaque champ divulgué est recomparé à la valeur on-chain).

Entrée

timestampintEpoch ms, au moment de la signature

5.Émission de documents

Module documents. Réservé aux comptes institutionnels (ISSUER, VERIFIER, NOTARY, ADMIN) — c'est le point d'intégration attendu pour qu'une université ou une entreprise émette automatiquement un diplôme ou une attestation depuis son propre système (scolarité, SIRH...).

POST/documents/issue
Authentification requise : Oui  ·  Qui : ISSUERVERIFIERNOTARYADMIN

Émet un nouveau document : mint du NFT on-chain, génération automatique du PDF représentatif, upload IPFS, indexation applicative. Le couple (doc_type, doc_key) doit être unique sur toute la plateforme ; un contenu identique ne peut pas non plus être réémis sous une autre référence.

Le champ file_content est obligatoire dans le schéma mais actuellement ignoré côté serveur : le PDF est toujours régénéré automatiquement à partir des attributes fournis. Envoyer n'importe quelle valeur non vide (ex. "placeholder") pour satisfaire la validation.

6.Gestion des comptes rattachés

Module identity. Permet à une institution de créer, depuis son propre SI, les comptes de ses étudiants/employés/clients, avec génération automatique de leur identité numérique (DID) et de leur pièce d'identité (ID_CARD).

Authentification requise : Oui  ·  Qui : ISSUERVERIFIERBANK

7.Workflows métier

Module documents. Machine à états générique utilisée pour la vérification de diplôme, la vérification d'attestation d'emploi et l'instruction d'une demande de prêt. Cycle : PENDING → IN_PROGRESS → AWAITING_VERIFICATION → IN_PROGRESS → AWAITING_NOTARY → COMPLETED (ou REJECTED/CANCELLED à toute étape autorisée). Le transfert de titre foncier suit un circuit séparé, plus fort cryptographiquement (§8).

POST/workflows/create
Authentification requise : Oui  ·  Qui : tout compte authentifié (l'appelant devient l'initiateur)

Démarre un nouveau workflow.

7.2 Actions sur un workflow existant

Chaque action renvoie la même forme de réponse : { "workflow_id": <int>, "status": <nouvel état> }. Toutes exigent une authentification, et seule la partie autorisée pour l'étape peut agir (initiateur, vérificateur désigné ou notaire désigné selon l'action).

Méthode & cheminQuiEntrée (corps JSON)Effet
POST /workflows/{id}/startInitiateur—PENDING → IN_PROGRESS
POST /workflows/{id}/request-verificationInitiateur{ verifier_id, verification_data? }→ AWAITING_VERIFICATION
POST /workflows/{id}/submit-verificationVérificateur désigné{ is_valid, notes? }→ IN_PROGRESS ou REJECTED
POST /workflows/{id}/request-notaryInitiateur{ notary_id }→ AWAITING_NOTARY
POST /workflows/{id}/validate-by-notaryNotaire désigné{ is_valid, notes?, transaction_hash? }→ COMPLETED ou REJECTED
POST /workflows/{id}/cancelInitiateur{ reason? }→ CANCELLED (impossible si déjà COMPLETED/REJECTED)

10.Notifications

Module backend (core). Permet à un SI partenaire de relever les événements concernant ses comptes gérés (document reçu, transfert accepté...) sans avoir à interroger chaque endpoint métier individuellement.

Méthode & cheminEntréeSortie
GET /notifications—[{ id, type, message, workflow_id, token_id, read, created_at }]
POST /notifications/{id}/read—Marque une notification comme lue
POST /notifications/read-all—Marque toutes les notifications comme lues
DELETE /notifications—Purge les notifications de l'appelant

Toutes exigent une authentification. Types de notification rencontrés : document_issued, transfer_request, transfer_accepted, notary_requested, transfer_completed.

10.5 Canal temps réel (optionnel)

Un WebSocket ws://{hôte}:8000/ws/{user_id} pousse les mêmes événements en temps réel, pour un SI souhaitant éviter le polling de GET /notifications. Format des messages poussés :

{ "type": "document_issued", "token_id": 118, "doc_type": "DIPLOMA" }

12.Hors périmètre de ce document

Les endpoints suivants relèvent de l'administration de la plateforme TrustWedge elle-même (rôle ADMIN, exploité par l'équipe TrustWedge) et non d'une intégration par le SI d'une institution partenaire — ils ne sont donc pas détaillés ici :

  • POST /admin/actors/create — provisionnement initial d'un compte institutionnel (fait par TrustWedge à l'onboarding d'un partenaire)
  • POST /admin/actors/{id}/set-password — définition du mot de passe d'un acteur nouvellement créé
  • POST /admin/land-titles/ocr-extract, POST /admin/land-titles/import — import assisté de titres fonciers existants
  • GET /admin/documents, GET /admin/workflows — vue d'ensemble de tous les documents/workflows de la plateforme
  • GET /stats/overview, GET /stats/activity, GET /network/status — indicateurs de supervision de la plateforme

Pour toute question sur l'onboarding d'une nouvelle institution ou l'accès à ces fonctions, contacter l'équipe d'exploitation TrustWedge.
